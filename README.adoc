=== Kiokový mód

Pro zobrazení kalendáře bez ovládacích prvků použijte `kiosk=true` parametr: https://svoz.litovle.cz/?kiosk=true

== Obsah repozitáře

Velmi jednoduchý a naivní skript pro vygenerování `ics` souborů a `csv` souboru se svozy odpadů pro jednotlivé ulice i místní části.

Soubor `ics` lze importovat do Google kalendáře a pravděpodobně i dalších aplikací. Kalendáře jsou ke stažení ve složce link:calendars/[`calendars`].

Soubor `csv` slouží primárně jako zdroj dat pro link:index.html[index.html] dostupný z https://svoz.litovle.cz

Vizuální pravidla a povolené prvky rozhraní jsou popsané v link:DESIGN.md[`DESIGN.md`]. Nové obrazovky mají používat sdílené CSS tokeny a komponenty namísto zavádění dalších variant karet, rámečků a štítků.

== Lokální build a validace

Projekt používá Python 3.12. Závislosti jsou deklarované v link:requirements.txt[`requirements.txt`].

[source,sh]
----
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python scripts/validate_project.py
python scripts/build_site.py --output-dir _site
python scripts/validate_site_artifact.py _site
----

Výsledný deployovatelný web je ve složce `_site/`, která se necommituje. Pro lokální vývoj jej lze jedním příkazem sestavit a spustit na `http://127.0.0.1:8000/`:

[source,sh]
----
python scripts/serve_site.py
----

Volby `--host`, `--port` a `--output-dir` umožňují změnit adresu, port a pracovní adresář. Po změně zdrojů je zatím potřeba server ukončit a spustit znovu, aby se web znovu sestavil.

=== Co je zdroj a co je generated výstup

Autoritativní zdroj pravidelného harmonogramu je v Pythonu, jednorázové změny jsou v `data/svoz_exceptions.json` a městské podklady jsou v `resources/`.

Repozitář odděluje autoritativní zdroje od deploy artefaktu:

* trackované validační snapshoty: `calendars/` a `waste_schedule.csv`
* ignorované generated stránky: `index.html`, `ulice/`, `bio/`, `sitemap.xml`, `_site/` a `resources/social/*.png`

HTML stránky, sitemap a social preview obrázky se generují až do deploy artefaktu, protože jejich obsah závisí na datu sestavení a změna jedné šablony nebo CSS by jinak vytvářela stovky odvozených změn v Gitu. Jejich správnost kontroluje CI sestavením a validací čistého `_site/`. URL social preview obrázků používá stabilní název souboru a query parametr `?v=...`, který se změní při změně obsahu obrázku.

Kalendáře v `calendars/` jsou trackované záměrně. Slouží jako validační snapshoty změn svozu a současně jako veřejné soubory pro existující odběry kalendářů. Pro každou lokaci se zatím generují dvě URL varianty: původní název s diakritikou a stabilní slug bez diakritiky. Web používá slug variantu, ale původní názvy zůstávají kvůli zpětné kompatibilitě s už importovanými kalendáři.

== GitHub Actions

GitHub Pages musí být nastavené na nasazování přes GitHub Actions, ne přímo z větve.

Workflowy:

* `CI` běží na pull requestech, pushi do `main` a ručně. Instaluje závislosti, spouští projektovou validaci, sestaví `_site` a validuje artefakt.
* `Deploy generated site` běží po pushi do `main`, ručně a denně v `03:17 UTC`. Sestaví aktuální `_site` a nasadí ho přes GitHub Pages artefakt.
* `Watch Litovel.eu` běží denně v `06:17 UTC` a ručně. Pouze hlásí kandidátní články z webu města, nic nemění.
* `Notify app on change` běží při pushi do `main`, pokud se změní kalendáře nebo zdrojové soubory ovlivňující harmonogram. Posílá FCM refresh do Android aplikace.

=== Přidání změny svozu

1. Ověřit oficiální zdroj a uložit odkaz včetně archivu.
2. Přidat jednorázovou změnu do `data/svoz_exceptions.json`; Python logiku měnit jen pokud změna vyžaduje novou skupinu nebo pravidlo.
3. Spustit `python generator_svozu_odpadu.py`, aby se aktualizovaly trackované CSV a ICS snapshoty.
4. Spustit `python scripts/validate_project.py`.
5. Pro kontrolu produkčního artefaktu spustit `python scripts/build_site.py --output-dir _site` a `python scripts/validate_site_artifact.py _site`.

== Zdrojová data

Zdrojová data se nachází v link:resources/[resources/]. Jsou to letáčky distribuované městem v PDF podobě. Součástí repozitáře jsou proto, aby byly dohledatelné případné změny.

=== Bio kontejnery

Dočasná přistavení velkoobjemových kontejnerů na bioodpad jsou oddělena od pravidelného svozu podle ulic. Roční strojově čitelné harmonogramy jsou v `data/bio_containers/{rok}.json`; aktivní soubor určuje link:data/site_config.json[`data/site_config.json`] a odkazuje na původní městské podklady v `resources/{rok}/`.

Model rozlišuje lokalitu, fyzické stanoviště a termín přistavení. Stanoviště nejsou navázána na seznam ulic. Unčovice proto obsahují dvě samostatná stanoviště (`u hasičárny` a `před Selikem`) a jednotlivé termíny odkazují na správné z nich. Termín je včetně prvního i posledního dne.

Souřadnice stanoviště jsou nepovinné, ale pokud jsou uvedené, musí obsahovat zeměpisnou šířku, délku a údaj o přesnosti. Web nabídne mapu pouze pro stanoviště označené jako přesné. Doplnění souřadnic nemění jednotlivé termíny.

Každá stránka ulice s dostupnou polohou zobrazuje tři nejbližší právě přistavené kontejnery, případně nejbližší stanoviště z následujícího termínu. Vzdálenosti se počítají při sestavení webu a nevytvářejí vazbu mezi ulicí a stanovištěm. Přibližné středy ulic a místních částí pocházejí z OpenStreetMap a jsou uložené v link:data/proximity_coordinates.json[`data/proximity_coordinates.json`]. Pokud pro ulici nebo stanoviště neexistuje geograficky podložená poloha, web vzdálenost nevymýšlí a daný výsledek nezobrazí. Explicitní přesné souřadnice stanoviště automaticky nahradí přibližný bod při příštím sestavení.

Přesné souřadnice mají `accuracy: "precise"`; pouze ty umožní odkaz na mapu. Dočasná data mají `accuracy: "provisional"`.

Přibližné body lze znovu importovat z uloženého Overpass JSON exportu příkazem `python scripts/import_osm_proximity.py export.json`. Importér páruje názvy ulic a místních částí, zapisuje pouze nalezené prvky a vypíše nepřiřazené stránky a stanoviště.

Bio část používá stabilní, na roku nezávislé URL:

* `/bio/stanoviste/{id}/` pro aktuální stav a úplný harmonogram fyzického stanoviště,
* `/bio/pobliz/{slug-ulice}/` pro nejbližší aktuální nebo nadcházející kontejnery podle ulice či místní části.

Vyhledávání na `/bio/` nabízí obě skupiny odděleně a po výběru přejde na příslušnou staticky vygenerovanou stránku. Hlavní bio stránka zvýrazňuje právě přistavené kontejnery a nejbližší další termín; úplný roční harmonogram je sbalený a seskupený podle termínů.

Při přidání nového ročního harmonogramu:

1. Uložit původní PDF do `resources/{rok}/`.
2. Zkopírovat předchozí roční JSON do `data/bio_containers/{rok}.json`, ponechat stabilní ID stanovišť a souřadnice a nahradit zdroje a všechna zveřejněná období. Z termínů se nevytvářejí opakující se Python pravidla.
3. V `lokace_svozu.py` ověřit pravidelný svoz pro nový rok, přidat rok do `REGULAR_SCHEDULE_YEARS` a doplnit jeho explicitní `BIO_COLLECTION_WEEK_RULES`. Starý vzor se nesmí automaticky extrapolovat.
4. Přidat `data/news/{rok}.html`; soubor může být zpočátku prázdný.
5. V `data/site_config.json` nastavit veřejný `target_year`, `waste_active_year`, seznam zobrazovaných `calendar_years` a podle dostupnosti samostatně `bio_active_year` a `bio_schedule_file`.
6. V testech zachovat audit starého roku a přidat nový audit podle zveřejněných PDF.
7. Spustit projektovou validaci a sestavení webu popsané výše.

`project_config.py` je jediným zdrojem veřejného cílového roku, aktivních datových roků a rozsahu generovaných kalendářů. Pravidelný svoz a bio kontejnery mají nezávislé roky, protože město nemusí oba podklady zveřejnit současně. Pokud je bio harmonogram starší než `target_year`, bio stránky jej označí jako poslední dostupný a výslovně uvedou, že nový harmonogram zatím nebyl zveřejněn. Po vypršení všech jeho termínů stránky podle ulic stále ukazují nejbližší fyzická stanoviště, ale stará data neoznačují jako aktuální ani nadcházející. Build selže, pokud rok bio harmonogramu neodpovídá jeho názvu nebo obsahu, chybí zdrojové PDF či roční novinky nebo pravidelný svoz nebyl pro některý konfigurovaný rok explicitně schválen. Od 1. ledna rovněž selže nasazení se starším cílovým rokem nebo rokem pravidelného svozu, takže denní GitHub Action nemůže tiše publikovat loňský kalendář; starší autoritativní bio harmonogram však nasazení neblokuje.

=== Model svozu

Pravidelný harmonogram svozu zůstává v Pythonu v souboru link:lokace_svozu.py[`lokace_svozu.py`].

Jednorázové změny svozu jsou v link:data/svoz_exceptions.json[`data/svoz_exceptions.json`]. Každá změna má stabilní `id`, typ odpadu, dotčené lokace nebo skupinu lokací, akci a datum změny. Pokud se používá `affected_location_group`, seznam míst může být přiložen jen jako `affected_locations_snapshot`; samostatné `affected_locations` je autoritativní pouze bez skupiny. Objekt `source` musí obsahovat klíče `url` a `title`; krátký doklad z oznámení lze uložit do `source.evidence`.

Budoucí automatizace má upravovat pouze datový soubor s jednorázovými změnami, ne Python logiku pravidelného harmonogramu.
